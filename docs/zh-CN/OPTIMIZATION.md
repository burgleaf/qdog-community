# Web 性能与资源优化方案

本文记录 `codexpet.top` 的性能基线、优化决策、验收标准和回滚方式。目标是在不降低宠物展示质量、不削弱 SEO/GEO、不增加 Worker 实时读取的前提下，降低首页传输量、静态站点体积和 CI 运行成本。

## 2026-07-28 基线

| 指标                               |                    优化前 |
| ---------------------------------- | ------------------------: |
| 宠物数量                           |                       165 |
| 首页 HTML                          |                 577,096 B |
| 首页 RSC 文本                      |                 404,479 B |
| 完整宠物 JSON（紧凑格式）          |                 378,717 B |
| 首屏卡片动画估算（SSR 后随机重排） |               约 9.25 MiB |
| `web/out`                          |                约 850 MiB |
| `web/out/assets/previews`          | 约 831 MiB / 3,522 个文件 |
| 全部 GIF                           |              约 248.8 MiB |
| 全部动画 WebP                      |              约 441.5 MiB |
| 全部联系表                         |              约 124.4 MiB |
| main CI 重复生成预览               |      2 次 / 约 3 分 42 秒 |
| Web 生产依赖审计                   |       1 critical / 2 high |

统计读取已经改为部署时生成的静态 `stats.json`。普通浏览不调用 Worker，Worker 只保留安装和点赞写入。

## 约束

- 首页默认随机展示，不恢复为安装量排序。
- 统计不要求实时；失败时继续展示目录，不阻塞浏览。
- 保留每只宠物的详情页完整动作预览。
- 保留 README 和 PR artifact 的动画预览与 QA 能力。
- 不把生成预览提交到 Git；正式宠物目录仍只包含三件套。
- sitemap、JSON-LD、`llms.txt`、`pets.json` 和索引提交继续工作。

## 实施阶段

### 阶段一：安全与交付门禁

1. 升级 Next.js 和配套 ESLint 配置，清除已知生产依赖漏洞。
2. 构建不再忽略 ESLint。
3. PR 增加 Web lint 与静态导出构建。
4. main 只生成一次全量预览；校验、构建、artifact 和部署复用同一份结果。

验收：

- `npm audit --omit=dev` 无 high/critical。
- 根目录校验、Web lint、Web build 和 Worker tests 全部通过。
- main 流水线不再在两个 job 中分别执行 `npm run previews`。

### 阶段二：首页负载

1. 为画廊建立只包含搜索、卡片和分享所需字段的 `GalleryPet`。
2. 安装命令由 slug 在客户端确定性生成，不为每只宠物重复传输长字符串。
3. Hero 在构建时从静态统计快照选出六只热门宠物，不再重复请求和排序全部宠物。
4. 卡片先显示静态缩略图，只在鼠标悬停或键盘聚焦时加载动画。
5. 客户端挂载后继续进行 Fisher-Yates 随机排序；静态缩略图避免排序前后重复下载大动画。

复杂度：

- 搜索、统计合并和排序保持 `O(n log n)`；随机洗牌为 `O(n)`。
- 客户端常驻数据由完整详情对象改为有界的画廊 DTO。
- 首页仅发起一次静态统计读取。

验收：

- 首页 HTML 和 RSC 体积显著低于基线。
- 首屏卡片默认请求缩略图，不主动请求 18 个动画。
- 随机、热门、安装、点赞和名称排序继续可用。
- 鼠标、键盘、触摸和减少动态效果设置下均可正常操作。

### 阶段三：预览与缓存

1. 网站包只复制当前目录实际引用的缩略图、动画 WebP 和 README 兼容资源。
2. 联系表和未引用的 GIF 继续留在 CI artifact，不进入 Pages 部署包。
3. README 预览统一使用动画 WebP，避免网站同时托管两套动作格式。
4. 动画 WebP 使用有损高质量编码和较高效的编码方法；先抽样验证透明度、尺寸和主观画质。
5. 为哈希静态资源、预览资源和统计快照设置分层缓存。

容量策略：

- 每只宠物的网站文件数量与动作数量线性增长。
- CI artifact 保留完整 QA 资产，但 Pages 只保留运行时资产。
- 不引入 R2；只有 Pages 包体或文件数接近平台限制时再评估对象存储。

验收：

- 部署包不包含 `contact-sheet.png` 和 `gifs/`。
- 所有 HTML、README 和公开目录引用的预览 URL 都能在 `web/out` 找到。
- 抽样动画尺寸仍为 `384x416`，帧数、持续时间和 alpha 通道正常。
- SEO 与 AI 搜索访问检查继续通过。

## 失败与回滚

- 依赖升级失败：单独回退 `web/package.json` 和锁文件，不影响数据与预览改动。
- 画廊交互回归：卡片可临时固定使用 `previewImage`；详情页完整动画不受影响。
- WebP 画质不达标：恢复无损编码参数，部署筛选和首页减重仍可保留。
- README 无法展示动画 WebP：只为 README 列出的动作恢复 GIF 复制，不恢复全部 GIF。
- 缓存导致陈旧资源：降低预览缓存时间；更新后的 HTML、catalog 和统计快照仍使用短缓存。

## 持续观测

每次宠物数量明显增长或预览编码变化后，记录：

- 首页 HTML/RSC 字节数。
- `web/out` 总体积、文件数和预览体积。
- 前 18 张缩略图与动画的总字节数。
- CI 预览生成、构建和部署耗时。
- Worker 每日请求、有效安装、点赞和错误数。
- `npm audit`、Web lint/build、SEO 和 AI 访问检查结果。

Worker 路由迁移不是当前阶段的优先项。只有无效调用持续增长并接近免费额度时，才评估从 Custom Domain 迁移到精确匹配写入路径的 Worker Routes。

## 2026-07-28 实施结果

三阶段优化已完成，最终本地静态导出结果如下：

| 指标               |              优化前 |    优化后 |   变化 |
| ------------------ | ------------------: | --------: | -----: |
| 首页 HTML          |           577,096 B | 334,191 B | -42.1% |
| 首页 RSC 文本      |           404,479 B | 176,320 B | -56.4% |
| Pages 静态包       |          约 850 MiB | 238.3 MiB | -72.0% |
| Pages 预览资源     |          约 831 MiB | 221.2 MiB | -73.4% |
| Pages 文件数       |               3,927 |     2,114 | -46.2% |
| 动画 WebP 源文件   |           441.5 MiB | 225.1 MiB | -49.0% |
| Pages GIF / 联系表 |        约 373.2 MiB |         0 |  -100% |
| Web 生产依赖审计   | 1 critical / 2 high |         0 | 已清零 |

首页只传输画廊和合集所需字段，Hero 热门宠物由构建时静态快照选择。画廊和合集默认请求缩略图；画廊卡片在悬停或键盘聚焦时才切换动画。Hero 保留六只动画宠物作为首屏动态展示。

main 流水线仍生成完整 GIF、WebP 和联系表并上传 QA artifact，但 Pages 只复制 1,541 个动作 WebP 与 165 个缩略图。新增 bundle 检查会阻止 QA 文件误入部署包，并验证公开目录引用的预览文件没有缺失。

GitHub 官方动作已升级到原生 Node 24 的 v7，Cloudflare Wrangler Action 已升级到 v4；同时移除了强制运行时兼容开关和 Node 20 弃用警告。
